# Sync P2 progress

Status: complete on 2026-10-10. Commits and push wait for a request. See [plan](plan.md) and [tasks](tasks.json).

## W1: sync health in every shell (complete)

- `syncNotice(state, now)` in `app-core/domain/sync.ts` chooses one message: needs attention, first sync failed (with retry), offline with saved changes, or still uploading once a change has waited 15 seconds. It returns nothing when the device has nothing left to send. Web renders it in `AppShell`; mobile renders it above the tab bar on every tab instead of only on Today.
- A first sync counts as failed after a download error or 20 seconds without completing. Retry re-runs `connectPowerSync`.
- Session client: a refresh whose rotated tokens fail to save keeps the old tokens, retries with the same attempt ID, and does not sign the user out.
- Evidence: 9 sync-state unit tests, 10 session-client tests, lint and typing for web, mobile and app-core.

## W2: read-after-command catch-up (complete)

- `expectArrival(key, arrived)` records the result a successful command expects; `useArrival(key, current)` reports `arriving` for 15 seconds, then `late` for up to two minutes, then trusts the replica again.
- Recording an invoice payment sets the expected balance; the invoice shows "Payment received. Updating the balance on this device." and hides Record payment until the balance arrives. Collecting a deposit does the same for the booking. Both remove a double-charge window where the replica still showed the old balance.
- POS sales already track paid state locally. Push notifications do not open records yet, so "notification before its row" does not apply.
- Evidence: 3 arrival-state unit tests; `apps/web/e2e/catchUp.e2e.ts` answers the payment command without writing data, so the replica never catches up, and passes against the local stack.

## W3: replica security evidence (complete)

- `stream_columns()` parses each stream's explicit projections. `tests/test_sync_projections.py` compares them with `tests/fixtures/sync_projections.json` and rejects pay, tax and billing columns in any stream that staff, contractors or the shared audience receive. Adding `rate_cents` to the limited staff stream fails both checks.
- The real-service suite opens a replica whose local schema declares every model column, so any column the service sends is stored. For each of six identities, every row in every synced table must belong to an allowed business and carry no non-null column outside that identity's streams. Fixtures now include bookings, an invoice and payment, a pickup order and line, and a balanced staff earning.
- Negative run: with `rate_cents` added to the limited stream, the staff and contractor checks failed and named each leaked row; the rules file was restored afterwards.
- Rotation drill (in `make test-sync`): a new signing key is accepted about 0.5 seconds after rotation, the previous key keeps working during overlap and from a second process, and a retired key is refused after about 299 seconds, matching the five-minute token lifetime. The drill fails if retirement takes longer than six minutes.
- Evidence: 25 real-service cases pass, including the 6 new per-role projection checks.

## W4: hours conflicts on device (complete on Android)

- Run on the Android emulator against the local stack, with Hannah's week recorded first and restored afterwards. The restore wrote explicit closed rows for Monday and Sunday, which changed their meaning: a weekday with no rows means no hours are set and the person can be booked at any time. Those two rows and the run's sync receipts were removed afterwards, returning the demo data to its seeded state; the 17 backend failures they caused were cleared by that cleanup.
- Offline edit shows "Saved on this device"; the edit survives a force-close and relaunch; a concurrent change from the host moves the server revision; on reconnection the device receives 409 and shows the conflict.
- "Apply my changes" previously sent the whole local week and discarded the concurrent server change. Each proposal now stores the week it was edited from, and a conflict shows the server's current week with only the user's changed days laid over it (`rebaseWeek`). After the fix the run kept the host's Tuesday change and the device's Monday change, with one row per weekday.
- Found and fixed along the way: the editor sent `expected_revision: null` when the replica had no revision, which the server refused with 422 and the editor showed as a conflict. It now waits with "This schedule hasn't finished syncing to this device", and a non-conflict refusal has its own message. The local PowerSync service had been running rules from before `hours_revision` existed; it was restarted to load the current config.
- PowerSync logs every transient disconnect as a console error, which showed as a red overlay in development builds. Those states already appear in the sync banner, so the mobile app filters that message from LogBox.
- Limits: the iOS simulator cannot be taken offline per app, so iOS was checked online only. A cold start leaves Today blank for about 44 seconds after the bundle loads (about 24 seconds before the sync stream opens and 20 after its first checkpoint); this is recorded for follow-up. The week command always stores seven rows, so saving the editor once turns days with no hours set (bookable at any time) into explicit open or closed days; the editor shows such a day as open 9 to 5 on weekdays. Whether "no hours set" should stay expressible in the editor is a product decision.

## W6: replication least privilege and monitoring (complete)

- `backend/scripts/db_access.py` replaces `infra/powersync/bootstrap.sql`. Its `roles` phase (run by `make up` and before migrations) creates `clientbridge_migrator`, `clientbridge_api`, `powersync_source` (with `REPLICATION`) and `powersync_storage_owner`, gives the migrator ownership of existing tables and functions (extension members excluded), sets default privileges so the API can use tables the migrator creates, and makes the storage role own `powersync_storage`. Its `grants` phase (run after migrations) grants data access to the API, `SELECT` on the synced tables to the replication role, and sets the `powersync` publication to exactly the synced tables. A publication for all tables is replaced in one transaction.
- Connections: `DATABASE_URL` uses `clientbridge_api` (API, tests, scripts); `MIGRATION_DATABASE_URL` uses the migrator (Alembic, the demo seed, which pauses the ledger's append-only trigger, and one owner-level test fixture); PowerSync replicates and stores through its own roles. CI and the verification stack use the same split, with the service superuser only as `ADMIN_DATABASE_URL`.
- Applied to the main local database: 46 tables and both ledger functions now belong to the migrator, the publication lists the 35 synced tables and none of the server-only ones (sessions, tokens, sync receipts, commands, audits, webhooks, returning challenges), PowerSync streams as `powersync_source`, and the local API runs as `clientbridge_api`.
- `make replication-health` reports readiness, the PowerSync slot, retained WAL and replay lag, and fails above 1 GiB of retained WAL or 60 seconds of lag; `make test-sync` runs it on the disposable stack.
- Evidence: the real-service suite (25 cases and the rotation drill) passes with all four roles created from scratch; the backend suite passes as `clientbridge_api` once the W4 test side effects were removed.

## W8: attachments and device storage (complete)

- `files.uploaded_at` (migration `cbsync05`) is set by `POST /v1/files/{id}/complete` and by `POST /form/{token}/upload/{file_id}/complete` for public form answers. Both read the object's size from storage first: a missing object is refused with 409 `upload_missing` and a size different from the one declared is refused with 422. Completing again returns the original time. Completing a public image or logo requires an owner or admin, as creating one does.
- Rows without `uploaded_at` are pending. Public media, item images, the business logo, form submissions and the app-core catalog, POS and online booking queries ignore them, so an interrupted upload never shows a broken image or attaches to a record. Retrying an upload creates a new row; `prune_pending_files` (hourly, minute 20) deletes pending rows older than 24 hours together with their objects. The existing `prune_uploads` job was renamed `prune_receipts` to match what it deletes.
- The main local database was backfilled from a storage check: 75 rows marked uploaded, none missing. The demo seed marks its files uploaded.
- Device storage: on web the app asks the browser to keep its storage persistent when the replica opens, so it is not evicted under storage pressure; eviction can still happen if the user clears site data, and then the replica downloads again and any unsent hours edit is lost. A full device (a SQLite "disk is full" or browser quota error) now shows its own sync problem instead of a download failure. An upload that cannot reach the server says it needs a connection rather than asking the user to retry blindly.
- Same-user data during reauthentication: when a refresh is refused, the shell removes the replica from the screen and shows sign-in; the replica and its pending work stay on the device and reopen only for the same account, as before. Signing out clears it.
- Offline files: file metadata syncs but bytes do not. Images that cannot load (offline or missing) already fall back to the item's initial; no other file bytes are shown in the apps yet. Browser storage is not encrypted at the application level and does not protect against a script running on the same origin; mobile storage relies on the platform's file protection, and tokens are in SecureStore. On-device database encryption remains out of scope.
- Evidence: backend suite (1357 passed, 95% branch coverage) including complete-once, 409, 422, cross-business 404, staff 403, pending media and logo, and pruning; three public form upload tests; storage-full unit tests; app-core SQL tests showing a newer pending image is skipped; frontend lint and typing.

## W7: scale (complete, with a recorded limit for the largest tier)

- Harness: a disposable verification stack per tier, seeded with generated clients, threads, messages, slots, bookings, invoices, payments and balanced ledger journals for one business, then a real web replica (Chrome, PowerSync web SDK, the production AppSchema) syncing as the owner. The opt-in spec is `packages/sync/e2e/scale.e2e.ts`; the driver, fixtures and raw results are in `.scratchpad/sync-p2/w7/`. Each query runs with the business-scoping wrapper the app uses and without it; times are medians of three warm runs.
- First run (1k clients, about 115k rows) found minute-long lists: clients 63 s, client directory 65 s, today's agenda 17 s, the schedule 136 s. Two causes, both on the device: without table statistics SQLite chose the `business_id` index and scanned a business's whole ledger once per client, and SQLite does not use a replica expression index on the right side of a LEFT JOIN, so every slot scanned all bookings.
- Fixes: the replica controller runs `PRAGMA optimize=0x10002` after the first sync; generated replica indexes drop a leading `business_id` (a device reads one business at a time) and add `entries.source_id` and `payments.client_id`; the four slot-to-bookings joins go through `slotBookingsJoin`, which joins by id. No server schema changed.

- At 50k clients and 1.36M rows the service sent 822 MB of row data (69 MB compressed) and the replica reached 1.69 GiB. Queries that are bounded in rows still scan whole tables there: the unread-message badge takes 1.3 s, the overdue-invoice badge 7.2 s and the agenda (388 rows) 2.4 s, because time-range filters go through `utcSql` and cannot use an index and badge counts scan every message or invoice. Paging the lists does not fix those.
- Decision (2026-10-10): devices keep a rolling window of history instead of everything; money tables stay fully synced so balances, invoice status and lifetime value remain correct offline.
- Approved schema change: `bookings.starts_at` (migration `cbsync06`), a copy of the slot start written when a booking is created and by `move_slot` whenever a slot moves, backfilled from slots (587 of 587 rows on the main local database). Sync streams cannot read the current time, and windowing bookings through their slot made PowerSync create a bucket per slot and fail at its limit of 1000 (`PSYNC_S2305`).
- Streams: messages, slots and bookings left the auto-subscribed streams for `history_shared`, `history_self` and `history_full`, which keep the same audiences and filter by `substring(<time>, 1, 7) IN subscription.parameter('months')`. The replica controller subscribes them before connecting with the past 12 months and the next 24 (`historyMonths`), so the first sync includes the window; rows leave the device when a month drops out of the subscription and its 24-hour TTL ends.
- Older history comes from the API while online: `GET /v1/bookings/visits` (a client's visits before a point, keyset paged, staff limited to their own, plus the count and date of completed visits before it) and `GET /v1/threads/{id}/messages` (a thread's older messages, keyset paged). The client record adds the server's earlier completed visits to its visit count and last visit; the conversation has "Show earlier messages" on web and mobile, and no longer jumps to the newest message when older ones load. A pet card's last visit and other per-visit summaries cover the window only.
- `useInvoiceRecord` reads one invoice by id (`INVOICE_SQL`) instead of loading every invoice.

- Limit: at 50k clients the remaining slow screens are the ones derived from the fully synced ledger (300k entries, 100k invoices). Up to 10k clients every measured list except invoices is under 250 ms.
- Evidence: backend tests for both history reads (paging, staff scoping, cross-business 404, auth and limits); the real-service suite subscribes history for each identity and asserts exact rows, including a three-year-old booking that no identity receives; raw results in `.scratchpad/sync-p2/w7/windowed/`.
