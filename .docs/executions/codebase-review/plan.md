# Codebase review plan

**Status: planned, not started.** This plan covers every finding from a full codebase review of `main` at `7ec6612e` (the merged Stripe Accounts v2, platform plans and tax engine work). It lists 3 High, 21 Medium and 27 Low findings, the 11 findings we refuted, and 19 dependency-ordered tasks in the [task queue](tasks.json). Implementation starts only on the user's go; commits, pushes and schema changes stay separate approvals, consistent with `CLAUDE.md`. Snapshot evidence and the location of every verification report are in [progress](progress.md).

## How the review was run

We reviewed the codebase at `7ec6612e`. The review began on `08eb5c9f` and was re-checked on the Stripe branch head `bfb46f1b`, whose content is identical to the merge commit. It ran in three stages, each reading the code directly, with no tests run against the shared database.

1. **Repowise.** Repowise 0.56.0 ran locally with `--no-prose`, a mock embedder, telemetry off and no provider keys in the environment, so no code or usage data left the machine. It produced a health score, a ranked list of files to fix first, static performance risks and dead-code candidates. On the first run its default editor setup also wrote an MCP server and hooks into the user's global Claude Code settings; the re-run used `--no-editor-setup`.
2. **Our analysis.** Five reviews read the code from different angles: backend defect risk (churn, fix history, complexity and test coverage, then the riskiest files line by line), backend performance (queries in loops, blocking calls, indexes, unbounded reads, jobs, sync streams), the frontend (app-core view-models, web, mobile and Connect), dead code and test gaps, and a functional map of every concept with its surfaces, tables, invariants, external services and tests.
3. **Verification.** A second pass took each finding from both sources and tried to disprove it by tracing callers, database constraints, indexes in models and migrations, webhooks, Stripe semantics, server-side deduplication, proxy configuration and tests. Each finding came back confirmed, partial or refuted, with a severity and a file:line reference. A third pass re-checked every surviving finding on the Stripe branch head, re-ran Repowise there and reviewed the code the Stripe work added.

Severity reflects impact on a live business and likelihood at launch scale (tens to hundreds of businesses, thousands of clients each): **High** loses or repeats client-facing actions, or blocks a launch criterion; **Medium** produces wrong money or data in a reachable path, or a cost that grows with normal use; **Low** needs an unusual sequence, is a convention gap, or only matters at much larger scale. No finding is Critical.

## What Repowise found

Repowise scored the repository 7.37 out of 10, with 11.2% of code volume at risk across 17 files. Its lowest-scoring files were `services/payments.py` (2.4), then `billing.ts`, `orders.py`, `bookings.ts`, `hours.ts`, `public.py`, `bookings.py`, `clients.ts` and `publicBooking.ts` (2.5 to 2.6). It checks its own score against history: 13 of the 20 lowest-scoring files had a bug fix in the last six months, against a 9% baseline. Its "fix first" list was to split `usePublicBookingFlow` (complexity 86) and `useDocComposer` (complexity 57), and to batch the queries in `pickup_windows`. Its "now" list asked to rotate two hard-coded credentials, and its dead-code scan reported five candidates at 40% confidence.

Its file ranking matched ours, and two of its findings held up: the `pickup_windows` query loop (M15) and the shape of the refund code in `payments.py` (L27). The credential, dead-code and untested-hotspot findings did not (see Refuted findings). Repowise does not reason about money, idempotency, concurrency or time zones, which is where every High and nearly every Medium finding below sits.

## What our analysis found

The money code is enforced well where it matters most: balanced, append-only journals and trigger-only balances in the database, every money status derived from the ledger, a nightly reconcile against Stripe, double-booking blocked by both advisory locks and GiST exclusion constraints, and column-level sync authorization that is tested. The weaknesses are in the paths around that core: notifications that are not durable, jobs that send before they commit, retries that mint new keys, Stripe calls made while database locks are held, public flows that bypass `run_command`, three separate refund paths, and documentation that no longer matches the code.
