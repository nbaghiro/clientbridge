# Google Business Profile schema proposal

Status: proposed only. No model or migration changes are included. `CLAUDE.md` requires explicit approval of concrete schema changes before implementation; this document supplies the purpose, fields, data impact and rollback for that review. Final migrations must also specify SQL types, CHECK constraints and indexes exactly before editing models.

## New operational tables

All tenant tables use prefixed ULID IDs, `business_id`, timestamps, scoped service access and database tenant policies. None is published to PowerSync. No table stores imported Google review bodies, names, photos or rating history.

Store OAuth state, browser binding, PKCE verifier and pending handoff handles in Redis with ten-minute absolute TTL and atomic consumption. Redis loss restarts authorization without compromising durable links. Cache access tokens only until expiry; never include credentials in generic webhook/audit/command payloads. OAuth temporary state is not a new persistent table.

Google response content is a bounded Redis cache with 24-hour TTL, outside SQL and backups. Validate that Redis persistence remains disabled and application clients never persist the Google response. On retrieval after an expired/missing entry, fetch upstream again. Location label/URL metadata follows the same TTL as review pages.

The user requested complete removal of internal feedback collection on 2026-10-18. The cleanup proposal replaces `reviews` with `review_requests`, preserves business/client/booking IDs and request timestamps, and removes ratings, comments, replies, public tokens, statuses and `businesses.review_hold_at`. Existing feedback cannot be recovered by a downgrade; backup restore is required. The user explicitly approved this cleanup on 2026-10-18. Migration cb0022 preserves only rows with an actual request timestamp, retains their IDs, removes the old table and moderation setting, and clears old review command replay payloads. The future Google integration must not restore these fields or any private feedback form.

Validate booking-client ownership in the service before requesting. Enqueue channel deliveries and request row in one transaction; link them by delivery scope. Explicit resend must create a new delivery attempt identity and obey limits; it must not create a second invitation identity for the same appointment.

## Approval and migration acceptance

1. Confirm one-location scope, proposed settings defaults, online-only Google tab, operational identifier retention and draft retention.
2. Inspect live duplicate counts read-only and finalize exact constraints before requesting schema approval. This plan has not accessed live customer data.
3. Present final model/migration diff with backfill, locking and index-build strategy. Approval of this planning PR alone is not approval to run a schema migration.
4. Test empty and seeded databases, tenant isolation, uniqueness races with independent sessions, grants, encryption rotation, task recovery, and feature-off compatibility with retained new columns.
5. Include database backup/restore handling: no imported Google content should exist in backups; restored credentials must stay feature-disabled until operator reconciliation confirms they were not revoked/disconnected after the snapshot. Persist or replay deletion/revocation records through the existing restore runbook rather than resurrect connections automatically.

## Google-first implementation slice — approval requested

The next slice requires OAuth and a selected Google location before review reads, replies or invitations. It adds the following two server-only tables; Pub/Sub event/account tables remain deferred. All `id` columns are text primary keys; all timestamps are `timestamptz`; `created_at` and `updated_at` are non-null with `now()` defaults. No Google review content enters SQL or PowerSync.

- `google_business_connections`: `id`; non-null unique `business_id` FK to businesses; non-null `connected_by` FK to users; nullable text `account_name`, `location_name`; nullable binary `refresh_token_ciphertext`; nullable text `key_version`; non-null text `state` CHECK selecting/active/reconnect_required/disconnected; non-null integer `generation` default 1 CHECK > 0; nullable timestamp `last_success_at`; nullable text `last_error_code`; timestamps. Index business_id; unique location_name where state=active. KMS encrypts refresh tokens with tenant/connection context; disconnect clears credentials and selected identifiers.
- `google_business_operations`: `id`; non-null `business_id` FK, `connection_id` FK, `actor_id` user FK, integer `generation` CHECK > 0; non-null text `kind` CHECK reply_put/reply_delete; non-null text `review_name`, `request_hash`, `idempotency_key`; nullable binary `request_ciphertext`; nullable text `key_version`, `expected_reply_revision`; non-null text `state` CHECK queued/running/confirmed/failed/unknown/canceled; non-null integer `attempts` default 0 CHECK >= 0; nullable timestamps `next_at`, `lease_until`; nullable text `error_code`; timestamps. Unique business_id/kind/idempotency_key; indexes business_id and state/next_at. Only owner-authored reply intent is encrypted here; terminal completion or seven-day expiry erases the payload. These operations preserve explicit intent across uncertain Google responses.
- Drop `businesses.google_review_url` and its API/sync field. Manually entered URLs are discarded; invitations require a connected location and use Google's location metadata. Existing invitation history is retained.

Purpose: durable authorization and safe reply intent, while Google supplies all displayed review content. OAuth handoff state and access tokens are short-lived in Redis; Google response data remains in foreground client memory or bounded ephemeral cache. Existing businesses start disconnected and must authorize Google. These changes do not create, edit or delete any customer Google review.

Rollback: disable the integration and retain the new encrypted operational rows until authorized cleanup. Dropping the two new tables would lose connections and pending reply intent; businesses would need to reconnect. A schema downgrade can recreate an empty manual URL column but cannot recover its values without backup. No live deployment is included in this implementation request.
