# Google Business Profile schema proposal

Status: proposed only. No model or migration changes are included. `CLAUDE.md` requires explicit approval of concrete schema changes before implementation; this document supplies the purpose, fields, data impact and rollback for that review. Final migrations must also specify SQL types, CHECK constraints and indexes exactly before editing models.

## New operational tables

All tenant tables use prefixed ULID IDs, `business_id`, timestamps, scoped service access and database tenant policies. None is published to PowerSync. No table stores imported Google review bodies, names, photos or rating history.

Store OAuth state, browser binding, PKCE verifier and pending handoff handles in Redis with ten-minute absolute TTL and atomic consumption. Redis loss restarts authorization without compromising durable links. Cache access tokens only until expiry; never include credentials in generic webhook/audit/command payloads. OAuth temporary state is not a new persistent table.

Google response content is a bounded Redis cache with 24-hour TTL, outside SQL and backups. Validate that Redis persistence remains disabled and application clients never persist the Google response. On retrieval after an expired/missing entry, fetch upstream again. Location label/URL metadata follows the same TTL as review pages.

The user requested complete removal of internal feedback collection on 2026-10-18. The cleanup proposal replaces `reviews` with `review_requests`, preserves business/client/booking IDs and request timestamps, and removes ratings, comments, replies, public tokens, statuses and `businesses.review_hold_at`. Existing feedback cannot be recovered by a downgrade; backup restore is required. The user explicitly approved this cleanup on 2026-10-18. Migration cb0019 preserves only rows with an actual request timestamp, retains their IDs, removes the old table and moderation setting, and clears old review command replay payloads. The future Google integration must not restore these fields or any private feedback form.

Validate booking-client ownership in the service before requesting. Enqueue channel deliveries and request row in one transaction; link them by delivery scope. Explicit resend must create a new delivery attempt identity and obey limits; it must not create a second invitation identity for the same appointment.

## Approval and migration acceptance

1. Confirm one-location scope, proposed settings defaults, online-only Google tab, operational identifier retention and draft retention.
2. Inspect live duplicate counts read-only and finalize exact constraints before requesting schema approval. This plan has not accessed live customer data.
3. Present final model/migration diff with backfill, locking and index-build strategy. Approval of this planning PR alone is not approval to run a schema migration.
4. Test empty and seeded databases, tenant isolation, uniqueness races with independent sessions, grants, encryption rotation, task recovery, and feature-off compatibility with retained new columns.
5. Include database backup/restore handling: no imported Google content should exist in backups; restored credentials must stay feature-disabled until operator reconciliation confirms they were not revoked/disconnected after the snapshot. Persist or replay deletion/revocation records through the existing restore runbook rather than resurrect connections automatically.
