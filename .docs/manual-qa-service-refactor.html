Before you start

Environment & preflight

Everything below runs against a locally-seeded stack. On staging, swap the hostnames/ports for the deployed URLs and use that environment's own Stripe test keys — the steps are identical.

1 · Bring the stack up (localhost)

cd ~/Documents/code/clientbridge
make up          # Postgres :8702 · PowerSync :8704 · Redis :8703 · MinIO :8705 · stripe-mock :8708
make migrate     # apply the schema
make seed        # load "Birchbark Pet Studio" — the fixture every test starts from
make dev-api     # FastAPI on http://localhost:8701
make dev-web     # provider/admin app on http://localhost:8700   (separate terminal)
# Connect (customer) app runs on http://localhost:8709 — start it if you test public links.

Ports: API 8701 · Web/provider 8700 · Connect/customer 8709 · Expo/mobile 8707 · Postgres 8702.

2 · Accounts (all seeded, password demo1234)

  • Owner — hannah@birchbarkpets.ca — full access (money, reports, settings).
  • Staff — diego@birchbarkpets.ca and priya@birchbarkpets.ca — limited role, used for permission tests.
  • Business: "Birchbark Pet Studio", slug birchbark → public booking page at http://localhost:8709/book/birchbark.
  • Pending invite: sam.newhire@example.com (for the staff-invite test).

3 · Getting an API token (for the curl-based steps)

API=http://localhost:8701
TOKEN=$(curl -s $API/auth/login -H 'content-type: application/json' \
  -d '{"email":"hannah@birchbarkpets.ca","password":"demo1234"}' | jq -r .access_token)
# use it as:  -H "Authorization: Bearer $TOKEN"
# For staff-permission tests, repeat with diego@birchbarkpets.ca to get a STAFF_TOKEN.

Every mutation endpoint also accepts an Idempotency-Key header; reuse the same key on a retry to confirm the response replays rather than double-acting.

4 · Firing Stripe webhooks (needed for every settlement test)

Card payments, package/gift-card activation, subscription billing, refunds, and payout allocations all complete only when Stripe's webhook is delivered — not the moment you click pay. In a real environment use the Stripe CLI to forward events to the API:

# one terminal — forwards live test-mode events to the local API
stripe listen --forward-to localhost:8701/webhooks/stripe
# it prints a signing secret (whsec_…); put it in the API env as STRIPE_WEBHOOK_SECRET and restart the API.

Then pay with test card 4242 4242 4242 4242 (any future expiry / any CVC) in the web or Connect UI. The webhook fires within a second or two; refresh to see the settled state. For ACSS/PAD (Interac-adjacent) use Stripe's test PAD flow. To advance recurring subscriptions, use a Stripe Test Clock (Dashboard → test clocks) or the CLI to trigger invoice.payment_succeeded.

If webhooks aren't wired, settlement-dependent tests (F, G, H, J, K, L, and the deposit half of I) will sit in "pending" forever — that's an environment gap, not a bug. Mark them blocked and note it. The Interac and totals/report tests do not need Stripe.

5 · What "validates" means on each card

Each test names the moved function it exercises, so a failure points straight at the batch to inspect. The refactor's two intentional behavior refinements are called out inline: Interac is now idempotent on the authed path too (M3) and remittance is served by ReportService behind the same route + gate (P-series).
