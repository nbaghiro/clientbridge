# Mobile product surface map

Reviewed October 8, 2026. This is the native counterpart to the [whole-product map](web-and-connect.md). It describes the current implementation, including embedded tabs, record views, editors, sheets, native integrations and incomplete paths. It is an implementation inventory, not a claim that every action has passed a device test.

There is **one provider mobile application**, built for iOS and Android from [Expo configuration](../../../frontend/apps/mobile/app.config.ts). There are not separate iOS and Android feature implementations or a native client-facing Connect app. Public booking, payment, forms, contracts, reviews and self-service links still lead to the browser-based Connect product. The mobile tree contains **32 screen modules, 20 composition modules and seven platform adapter modules**. A module is not one surface: Payments contains eight areas; Inbox contains five; client details open additional stack screens and sheets.

Mobile navigation now uses Today, Schedule, Clients and Inbox around the raised Create button. Payments opens as a stack screen from the Today summary shortcut or View payments in the Create sheet, retaining the originating screen on Back. Inbox preserves its selected section and conversation across bottom-tab switches; message notifications target their exact thread, and client message shortcuts open a draft when no thread exists.

## Runtime and construction

[App.tsx](../../../frontend/apps/mobile/App.tsx) composes SafeAreaProvider, authentication, PowerSync, Stripe, React Navigation and the native confirmation host. The app currently uses Expo 57, React Native 0.86.3, React 19.2.3 and React Navigation 7. The [package manifest](../../../frontend/apps/mobile/package.json) is the version reference. Native configuration comes from Expo plugins and autolinking; this app directory does not track separate `ios/` or `android/` projects. Native modules require a development or release build; Expo Go does not provide this app's SQLite and Stripe modules.

The shared implementation rule is visible throughout: domain hooks from `@clientbridge/app-core` own queries, form state, validation, authorization-aware actions, money calculations and command submission. Screens compose these hooks with the native half of `@clientbridge/ui`. The native UI is not the web app in a WebView. Tokens and copy are shared, while navigation, layout, text input, lists, keyboard handling, sharing and payments are native.

The boot token-read rejection is swallowed without changing `authed` from `null`, so an unreadable or malformed token store can leave the loading screen indefinitely. This is a source finding; that failure was not injected on the simulator. There is also a sign-out interval during which the authenticated tree remains mounted after credentials are cleared. These are distinct from normal login and logout behavior.

## Navigation and shell

The [navigation types](../../../frontend/apps/mobile/src/navigation.ts) and [root navigator](../../../frontend/apps/mobile/App.tsx) define four bottom tabs: Today, Schedule, Clients and Inbox. The [custom TabBar](../../../frontend/apps/mobile/src/components/TabBar.tsx) puts Create between Schedule and Clients, uses shared badge counts, and adds safe-area padding. Create opens an action grid for booking, sale, invoice, estimate, client, message and time off according to role, plus a View payments shortcut and recent-client “Book again” chips.

The root stack additionally registers Search, Notifications, Payments, Setup, GetSetUp, Taxes, Business, Services, Team, GettingPaid, ClientHistory, ClientPets, ClientWallet, OnlineBooking, Reminders, Classes and Recurrences. Login and onboarding are conditional roots, not stack routes. Payments and Inbox switch their subareas in place; they are not individual navigation routes. Most record details are bottom sheets; message threads and repeating-booking records replace the body of their parent screen.

Today has Search, Notifications and Setup controls and a Payments shortcut beneath its summary cards. Inbox is a permanent bottom tab with an unread-message badge; the old Clients-header shortcut is removed. Create → Message, search, client actions and message/review notifications also reach Inbox. Explicit message targets are consumed once so switching sections cannot reopen a canceled draft.

[useOpenLink](../../../frontend/apps/mobile/src/lib/links.ts) translates shared shell targets into native routes. That translation currently loses some meaning:

- `estimate` and `invoice` produce the same Payments parameters; `Invoices` interprets a create token as an **invoice**. The Estimate shortcut therefore does not request the estimate composer. The Estimates tab's own New estimate action is separate and correct in source.
- `checkout`, `sale` and `orders` all select Sales. Payments renders `<POS />` without the route's record ID or requested view. A checkout shortcut cannot select its booking, and an orders shortcut cannot select the orders board through this route.
- Recent-client “Book again” and the client record's booking action open a generic booking composer without preselecting the client.
- The client record renders History inside the phone-number condition, so a client without a phone number also loses that History entry point.
- `stock` and `catalog` both open Services without selecting Inventory.
- Inbox initializes its selected segment from route parameters once. It does not synchronize subsequent segment changes or normalize an incoming segment against the visible role-filtered set, unlike Payments. This is a navigation/UI policy inconsistency, not evidence of a server authorization bypass.
- A message link with a client ID opens an existing thread if found. It does not open a new composer for a client with no thread.

There is no NavigationContainer linking configuration or push-response navigation listener. Registering the `clientbridge` scheme alone does not implement invite, reset, payment-return or record deep links.

## Entry surfaces

### Sign-in, account creation and password reset

[Login](../../../frontend/apps/mobile/src/screens/Login.tsx) uses `useAuthForm`. Sign-in and signup share native email/password controls, password reveal, field errors, a busy submit button, lockout/attempt messages and Google entry. Signup adds a name and password guidance. The reset mode collects email; its sent state offers Open mail, resend cooldown and return to sign-in. Keyboard avoidance wraps a scrolling screen.

Google calls the explicit unavailable handler; it is not a functioning native OAuth flow. Reset-email request and sent states exist, but the navigator does not register a new-password screen. Staff invites are generated as web URLs; there is no native accept-invite screen. Demo owner credentials are supplied as defaults in this screen's source. No account/business switcher exists in the native shell.

### First business

[Onboarding](../../../frontend/apps/mobile/src/screens/Onboarding.tsx) uses the shared business onboarding form to collect the business's name, booking-page slug and province, with a province-specific tax summary, submit its creation and show the submitted/waiting state while PowerSync catches up. It retains sign-out. This is different from Get set up: onboarding creates the first business; Get set up helps an existing business finish configuration.

## Workday surfaces

### Today

[Today](../../../frontend/apps/mobile/src/screens/Today.tsx) chooses `useOwnerToday` or `useStaffToday` by payment-management capability. [TodayParts](../../../frontend/apps/mobile/src/components/TodayParts.tsx) renders the header, horizontal KPI cards, next/current booking, agenda, attention list, getting-started checklist and quiet-day state.

The owner view combines replica-backed agenda data with separately loaded server money aggregates: booked visits, still to collect, collected money and invoices awaiting payment. Loading and retry states are independent. Current/next cards expose booking lifecycle, checkout and messaging actions; “Needs you” links to overdue invoices, reviews, stock, tax and staff-pay work. The rest-of-day list and empty/setup states adapt to the available data. The staff version shows the person's next client, earnings, hours, tomorrow and messages rather than the business-wide management dashboard.

The offline banner appears here after a replica has synced; it is not a persistent banner across every tab. Five taps on the date within 1.5 seconds open [DebugOverlay](../../../frontend/apps/mobile/src/components/DebugOverlay.tsx). That gesture is wired without an explicit `__DEV__` guard in the current screen. The overlay exposes sync/replica diagnostics; assess that production exposure separately from the ordinary product navigation.

### Schedule, booking details and booking creation

[Schedule](../../../frontend/apps/mobile/src/screens/Schedule.tsx) uses `useScheduleBoard`, `useBookingDetail`, `useBookingActions` and `useBookingStart`. Its native presentation is a **single-day staff-lane calendar**, with a seven-day date strip and previous/next week controls. It lays out overlapping events, working hours, off-hour spans, closures/time off and the current-time marker. Lanes divide the available width; this is not the desktop day/week calendar with native drag and resize.

Tapping an event opens a DetailView with [BookingSheet](../../../frontend/apps/mobile/src/components/BookingSheet.tsx) content and an action bar. It includes client/pet/service/staff/time, notes, add-ons, station assignment, deposit/payment context and lifecycle controls. Reschedule opens a separate sheet. Cancellation and no-show actions have their own confirmation state; completion invokes the shared lifecycle action. Deposit collection can open a shared ChargeSheet. Related client history, messaging and invoicing are linked from the record.

New booking opens BookingComposerSheet with client/pet, service, staff, date/time, repeat, notes and client-notification controls. The default slot is 10 AM on the selected date for the first working lane (falling back to another lane/viewer). Shared validation checks availability and other business rules; the booking and rescheduling sheets use DateStrip and TimeSlotPicker to present available dates and times. Opening an existing booking from a route adjusts the focused day before selecting it.

### Classes

[Classes](../../../frontend/apps/mobile/src/screens/Classes.tsx) uses `useClassBoard`. It has session selection, capacity/seats, roster, attendance, waitlist, search/add, individual and all-person check-in, undo, no-show and promotion. The message-everyone sheet composes a real class message. Those controls mutate attendance, roster or messaging through shared commands; opening the screen is not proof that all those operations have been exercised.

### Repeating bookings

[Recurrences](../../../frontend/apps/mobile/src/screens/Recurrences.tsx) implements a searchable series list, attention/ending filters, selected-series record and new-series composer as body states. The record includes upcoming dates, history and edit/cancel actions. The composer supports client/service/staff, first date/time, weekly/monthly recurrence, interval and count/until end conditions. Preview shows conflicts and skip/shift decisions before confirmation. Changes can target one, following or all visits, with notification choices. This is a substantial native workflow, not just a link to web.

## Payments: eight embedded areas

[Payments](../../../frontend/apps/mobile/src/screens/Payments.tsx) selects tabs using `visiblePaymentsTabs(role)` and normalizes the current selection to an allowed tab. The horizontal rail contains Invoices, Sales, Gift cards, Refunds, Staff pay, Tax returns, Payouts and Reports for the management role. Staff visibility is narrower. Only invoice/refund bodies receive the relevant incoming record parameters; POS does not.

### Invoices and estimates

[Invoices](../../../frontend/apps/mobile/src/screens/Invoices.tsx) contains separate invoice and estimate lists, status segments, search, totals/summary, details and lifecycle actions. Invoice detail includes payment and balance context, preview/share, sending/reminding, editing/voiding, recording payment and requesting e-Transfer. Estimates add acceptance/decline/conversion paths.

[DocEditor](../../../frontend/apps/mobile/src/components/DocEditor.tsx) is a large native modal composer: client selection; catalog or custom lines; quantity, unit price and tax; line/document discounts; optional estimate lines; terms/message; preview; draft/save/send; sent success and start-another. It uses the shared document form and explicitly handles unsaved edits. The editor's size is a consequence of rendering all document states, while money and validation remain shared.

[DocumentPreview](../../../frontend/apps/mobile/src/components/DocumentPreview.tsx) renders the shared letterhead/document primitives. Its share action sends the public document URL to the OS share sheet. It does not create a local PDF attachment.

[RecordPayment](../../../frontend/apps/mobile/src/components/RecordPayment.tsx) supplies full/partial amount, available methods, cash tender/change, date/reference/note and receipt behavior. [InteracRequest](../../../frontend/apps/mobile/src/components/InteracRequest.tsx) adds amount, channel, expiry, instructions/history and sending. Neither opening these sheets nor confirming local form validity establishes real provider settlement.

### Sales / point of sale

[POS](../../../frontend/apps/mobile/src/screens/POS.tsx) uses `useSale` with `platform: "mobile"`, the shared register catalog and checkout queue. The default view is the register. It shows today's visits, products/services, search/categories and a cart bar, with walk-in/client selection and package/plan/gift-card sale entry points. Item taps build the in-memory ticket.

[SaleTicket](../../../frontend/apps/mobile/src/components/SaleTicket.tsx) renders ticket, discount, payment and done states in a bottom sheet. It supports quantities, line/whole-sale discounts, discount reason and manager PIN policy, holding a sale, percentage/custom tips, tip allocation, cash/change, saved/new card and Tap to Pay. Completion offers SMS/email receipt or skip, then next booking/new sale. Receipt sending and payment confirmation are consequential commands, not display-only actions.

[SaleOrders](../../../frontend/apps/mobile/src/components/SaleOrders.tsx) implements the front-desk board and sale history. Board sections show held tickets, online orders to prepare and ready-for-pickup orders, with detail/resume/advance/notify actions. History is management-only. POS switches these views locally; the shell's `orders` target currently does not select the board.

### Gift cards, packages and plans

[GiftCards](../../../frontend/apps/mobile/src/screens/GiftCards.tsx) is broader than its tab label: `useEntitlementWallet` and detail hooks show prepaid visits, memberships and gift balances with client selection, liabilities and usage/history. It exposes selling, redemption, consumption, cancellation and refund routes. Detail content and actions depend on entitlement kind and status. The same sale components serve this area and client wallets.

### Refunds, credit notes and disputes

[Refunds](../../../frontend/apps/mobile/src/screens/Refunds.tsx) contains recent payments/search, credit notes and disputes. Selecting a payment opens a refund composer with full/partial allocation, reason, notification and a server-calculated preview before confirmation. The UI shows prior refunds and credit-note consequences. Disputes have their own list/detail and evidence/Stripe guidance. These are server-authoritative financial operations; their success/failure paths are not covered by a navigation-only walkthrough.

### Staff pay

[Earnings](../../../frontend/apps/mobile/src/screens/Earnings.tsx) shows to-approve, approved-to-pay and paid-this-year summaries. The reviewed iPhone and Android renderings show the three money values but collapse their labels out of the layout/accessibility tree. A regression test asserts those labels separately from the navigation smoke check. Selecting a member opens earning lines, selection/approval and recording payment. Rates and retail commission are configured in Team. This records staff earnings/payments; it is not a payroll processor with tax deductions and bank disbursement.

### Tax returns

[Remittances](../../../frontend/apps/mobile/src/screens/Remittances.tsx) uses `useTaxFilings` for federal/provincial liabilities, periods, due state and filed history. The filing sheet collects tax family, input-tax credit/adjustment information, confirmation and date through `useFilingForm`. The native renderer exposes filing recording; it does not expose the web renderer's separate paid-recording flow. Nothing here submits a return to government services.

### Payouts

[Payouts](../../../frontend/apps/mobile/src/screens/Payouts.tsx) shows funds in Stripe, recent deposits and fees, payout status/detail, returned-payout guidance and recent card charges. It is chiefly a read surface. Its three summary labels also disappear in the reviewed native rendering, like Staff pay, leaving amounts without their names. The UI explicitly notes that mapping a particular payout to its settled charges is not yet recorded; recent charges are not presented as a reconciled payout allocation.

### Reports and export

[Reports](../../../frontend/apps/mobile/src/screens/Reports.tsx) uses server money summaries and selected periods, then opens report DetailViews for income, item sales, GST/HST, provincial tax and T4A. Report rows, monthly bars and relevant summaries are rendered natively. CSV export calls `Share.share({ title: filename, message: csv })`: this shares text with a title, not an attached file. The bookkeeper panel offers individual exports; it does not create the web app's ZIP pack or browser print/PDF output.

## Inbox: five embedded areas

[Inbox](../../../frontend/apps/mobile/src/screens/Inbox.tsx) contains Messages, Reviews, Broadcasts, Forms and Contracts with role-filtered tab visibility. Its selected segment is local state initialized from route params, with the navigation caveat described above.

### Messages

`useInbox` powers unread/all/text/email filters, search and conversation rows. Opening a thread replaces the list. `useConversation`, `useMarkThreadRead` and `useThreadComposer` supply grouped message bubbles, read state, channel, quick replies, validation, counters and sending. A ScrollView moves to its end as content grows; KeyboardAvoidingView keeps the composer above the keyboard. STOP/consent state changes the available channels and warning copy.

New message is a native sheet with client, channel and body. Thread details open client context and actions. Viewing a thread can mark it read; that is a real state change even when no outbound message is sent. The walkthroughs avoid sending messages.

### Reviews

[Reviews](../../../frontend/apps/mobile/src/screens/Reviews.tsx) combines distributions, moderation filters, review records, suggested/edited replies, publish/hide, Google sharing and client messaging. Settings include low-rating handling and the Google review URL. Suggested recent visits and a request sheet initiate review invitations. Native `Linking` opens external review URLs.

### Broadcasts

[Broadcasts](../../../frontend/apps/mobile/src/screens/Broadcasts.tsx) includes audience counts, campaign status/results, opt-out and implied-consent lists, CSV text sharing and a three-step composer: audience, message, review. Channel/body preview, scheduling, final confirmation, duplication and cancellation are present. Sending/scheduling creates actual campaign work; this review does not submit one.

### Forms

[Forms](../../../frontend/apps/mobile/src/screens/Forms.tsx) includes the library with question/response/waiting counts and a full editor. Editor tabs are Questions, Client preview and send settings. Field-property sheets cover label, help, type, required/options, reorder and delete; save is explicit. SendToClientSheet targets a client through the shared form-send command. The library displays response counts, but this renderer is not a full response-review inbox.

The shared native [FormQuestion](../../../frontend/packages/ui/src/mobile/FormQuestion.tsx) renders preview controls. File/image/signature placeholders in that component are not wired to a native upload/capture flow. The presence of a generic native SignaturePad or ImagePicker elsewhere in the library does not establish that the provider form preview uploads files or captures client signatures. Actual client form submission remains on Connect.

### Contracts

[Contracts](../../../frontend/apps/mobile/src/screens/Contracts.tsx) implements template library, new-template name/body composer, template detail, requests/status, send/resend/share signing link and a signed-version document view. Existing contract text editing explicitly directs the user to web. Creating a new template and viewing a signed immutable version are supported natively; editing an existing template is a different capability. Clients sign in Connect, not an authenticated provider-native signing screen.

## Source inventory and coverage boundaries

Every screen module is accounted for above: **Login, Onboarding, Today, Schedule, Classes, Recurrences, Clients, Payments, Invoices, POS, GiftCards, Refunds, Earnings, Remittances, Payouts, Reports, Inbox, Reviews, Broadcasts, Forms, Contracts, Setup, Business, Catalog, Team, Hours, GettingPaid, Taxes, OnlineBooking, Reminders, Search and Notifications**.

Search uses the shared replica search, grouped hits, highlights, recent queries and create/navigation results in a dedicated safe-area screen. Notifications uses the shared seven-day derived feed, filters and per-device read/seen state. Its native click handler forwards an invoice record ID for overdue-invoice entries; other entries generally open the area instead of a specific record. Push registration is separate from this feed.

The 20 composition modules are also represented: **BookingSheet, ClientSheets, ClientScreens, DocEditor, DocumentPreview, EntitlementSales, GetSetUp, InboxButton, InteracRequest, ItemEditor, RecordPayment, SaleOrders, SaleTicket, Stock, Stripe, TabBar, Terminal, TodayParts, DebugOverlay, Loaded and SendToClient**. Loaded is the reusable async loading/error wrapper; SendToClient supplies the form/contract recipient sheet. These modules account for important surfaces that a route-only inventory would miss.

The iOS client-record walkthrough also exposed an editor transition failure: tapping Edit left the record visible instead of presenting Edit client. Clients keeps RecordSheet mounted while requesting ClientEditorSheet, making overlapping native modal presentation a likely cause; that cause remains an inference pending a dedicated fix. A focused regression is retained outside the passing navigation suite.

Two accessibility defects were corrected while making the native walkthroughs possible: the unnamed Inbox button and modal descendants hidden by their accessible backdrop parent. The main remaining implementation gaps are routing intent loss, native invite/reset entry, OAuth, push-tap/deep-link navigation, refresh-session revocation on logout, selected media/template/bank-account edits that remain web-only, native export format differences, and production debug access. These are tracked as findings here; the review does not silently substitute web behavior for absent native behavior.

## Repeatable native walkthroughs

The [Maestro flows](../../../frontend/apps/mobile/e2e) exercise the installed native app against the real local API and synced seed. They keep navigation checks and screenshots in the repository's testing workflow. They do not mock app-core, reset the business, clear the device keychain or submit messages/charges. They assume the seeded owner business and English copy. Run them on a dedicated development simulator signed out or signed in as the seeded owner, with the backend, sync service and Metro running.

Both an iPhone 17 Pro simulator (iOS 26.5) and a Shared Pixel emulator (Android 14 / API 34) have the native development build installed. Android uses ADB reverse for the local API, PowerSync and Metro ports. Runtime coverage is itemized by device below. React Native Web playground tests are useful component coverage but are not native Android or iOS execution.

### Device results and retained artifacts

The iOS run completed **6/6 walkthroughs in 4m 10s**, recording **58 screenshots** across owner workday, setup, payments, Inbox, client records, authentication and staff-role boundaries. Each flow uses the actual installed native build and real API/PowerSync data. See the [iOS HTML report](../../../.scratchpad/mobile-review/ios-final.html) and [test instructions](../../../frontend/apps/mobile/e2e/README.md). Reports are local ignored artifacts; the flow definitions and this map are retained in source.

The Android 14 / API 34 emulator also completed **6/6 walkthroughs in 7m 28s**, with **58 screenshots**, using the same flow files. See the [Android HTML report](../../../.scratchpad/mobile-review/android-final.html). Across both devices, that is 12 passing walkthrough executions and 116 captured screen states; it is not 116 distinct features or exhaustive state coverage.

The focused iOS [regression report](../../../.scratchpad/mobile-review/ios-regressions.html) has **three deliberately failing assertions against correct intended behavior**:

| Reproduction         | Observed result                                                                  | Implementation evidence                                                                                                                                |
| -------------------- | -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Create → Estimate    | New invoice appears instead of New estimate.                                     | `useOpenLink` merges invoice/estimate targets; `Invoices` creates invoice from the token.                                                              |
| Client record → Edit | The record remains visible; Edit client never appears.                           | The record and editor are separate simultaneously mounted NativeModals. Presentation stacking is the leading explanation, not yet a proven root cause. |
| Staff pay totals     | Amounts appear but To approve / Approved, to pay / Paid this year labels do not. | Horizontal summary groups compose row-oriented Stat controls whose label areas collapse. Payouts has the same visible symptom.                         |

The [Android regression report](../../../.scratchpad/mobile-review/android-regressions.html) reproduces the Estimate and Staff pay label failures, while **Client record → Edit passes on Android**. The client editor problem is therefore confirmed on iOS and is not a universal absence of that implementation. Both platforms also show the missing summary labels in Payouts screenshots.

These regression flows live under `e2e/regressions/`, outside the passing top-level navigation suite. They remain runnable and should move into normal coverage when fixed. The overview and smoke checks do not declare those surfaces defect-free.

Validation beyond the device walkthroughs: **`make check` passed**, including lint, all workspace type checks, structure/unused-code checks, generated-file consistency, **1,190 backend tests with 95.16% coverage**, and the frontend test targets (201 app-core tests and six site tests, reused from Turbo cache). The rebuilt playground's complete iPhone and Android story-render loops also passed. A workspace-local `UV_CACHE_DIR` was used because the normal uv cache was not readable.

The native runs do not certify real card settlement, physical Tap to Pay, Apple Pay/Google Pay, push delivery or tap routing, new-business creation, offline conflict recovery, every validation/error/empty state, release builds, iPad layout or all supported OS/device combinations. The deliberately limited transaction scope preserves the seeded business while making the navigation and composition review repeatable.
