# Backend principles review

The backend needs consistent rules for isolation, bounded work, concurrency and recovery across HTTP, PostgreSQL, PowerSync, background jobs and all three client runtimes. These rules are not yet enforced uniformly. The most important additions to the [original review](overview.md) are database role separation and RLS, complete list traversal without loading every row, and explicit contracts for concurrent edits and older mobile clients.

This is an analysis and implementation plan, not an implementation change. The [execution plan](../../executions/backend-hardening/plan.md) incorporates all 31 original findings and the 12 additional findings below. Execution began after the user's “go” and uses a low-effort subagent for bounded tasks under primary-agent review.

## Evidence and scope

The follow-up inspected the current working tree on 7 October 2026, including the API/service boundaries, session handling, database models and migrations, PowerSync configuration/schema generator, shared local SQL and transport, and web/native list components. Feature work is still changing this checkout; the original audit's 1,222-test result applies to its isolated snapshot, not these newer changes.

A read-only catalog query against the local development PostgreSQL 16.15 database found **44 public-schema tables including migration metadata, zero tables with RLS enabled or forced, and zero policies**. Its `clientbridge` role has `SUPERUSER`, `BYPASSRLS` and replication privileges. The development API and PowerSync configuration use that role. These are local facts, not evidence of the privileges in a production deployment.

## Where pagination belongs

Most staff-facing entities have command endpoints rather than GET collection endpoints. For example, `api/clients.py` contains mutations while `domain/clients.ts` reads SQLite. Adding REST list endpoints for every synced entity would create a second read architecture without fixing the current screens.

Use three distinct implementations: local query pages for already synced data; cursor HTTP pages for public or server-only data; claimed batches for jobs. Rendering virtualization and sync-volume limits are additional controls. PowerSync documents these as separate options for [infinite scrolling](https://docs.powersync.com/client-sdks/infinite-scrolling); partial synchronization changes what remains available offline.

| Surface and current source | Required behavior |
|---|---|
| Client directory, catalog/products and pickers — `domain/clients.ts`, `catalog.ts`, `pos.ts` | SQL filtering before paging; normalized name plus ID tie-break; search across the entire authorized local dataset, including choices outside the first page. |
| Invoices, estimates, sales, earnings — `billing.ts`, `pos.ts`, `earnings.ts` | Complete history with stable date/ID ordering, filters in SQL, independently computed totals and detail queries by ID. A detail must not disappear because its parent list page is unloaded. |
| Refund candidates, stock movements, payouts and charges — `refunds.ts`, `catalog.ts`, `payouts.ts` | Replace the 200/60/24/50 terminal caps with continuation; retain caps only for explicitly labeled previews linking to complete history. |
| Inbox and conversation — `messaging.ts` | Paged thread list and older-message loading, with message ID dedupe, preserved scroll anchor, live new messages and independent unread counts. |
| Client visits, notes, wallet, entitlement history — `clients.ts`, `entitlements.ts` | Parent-scoped history pages; pinned-note ordering, stable tie-breakers, aggregates independent of loaded pages. |
| Reviews, requests, signatures, broadcasts, template libraries — corresponding shared domain modules | Bounded history/library queries. Preserve the intentional eight-review-suggestion preview and six-public-review preview; they are not full-history APIs. |
| Global search — `domain/search.ts` | Apply search in SQL before limiting; per-kind continuation; remove the 300-booking blind spot. Do not advertise complete counts from a partial result. |
| Schedule, class rosters, availability — `bookings.ts`, `classes.ts`, public booking services | Bounded date windows or session capacity, not arbitrary infinite append. Load adjacent date windows when navigating. |
| Reports and exports — `api/reports.py`, `services/reports.py` | Complete SQL aggregates, cursor detail tables and streamed/background exports. Pagination must never change financial totals. |
| Public shop and large public service catalogs — `services/public.py` and Connect hooks | Bounded search/cursor reads when collections can grow; retain a backward-compatible first-page contract during native/web rollout. |
| Broadcasts and other jobs — `services/messaging.py`, scheduled `run_*` functions | Durable recipient/work batches. The current broadcast cap drops eligible recipients after 500; UI pagination does not solve it. |

## What RLS should and should not do

Use PostgreSQL RLS as an additional defense against missing tenant predicates in trusted backend code. Continue enforcing role, ownership, state and financial rules in services. PostgreSQL policies distinguish visibility from write checks; superusers and `BYPASSRLS` roles bypass them, and owners normally bypass them unless forced. Referential integrity checks also bypass RLS, which is why composite FKs are a separate requirement. [PostgreSQL 16 row security](https://www.postgresql.org/docs/16/ddl-rowsecurity.html).

RLS with a backend-set custom setting is not protection against arbitrary SQL execution using a compromised application credential: that credential can set the context too. Parameterized queries, restricted grants and trusted context construction remain essential. Public capability access needs narrower service and database paths than authenticated tenant access.

PowerSync download authorization remains a separate policy boundary. Its rules currently use membership-based buckets; restricting an API connection with RLS does not restrict an already replicated device. PowerSync describes database RLS and download filtering as [complementary controls](https://docs.powersync.com/integrations/supabase/rls-and-sync-streams). Role/tenant changes require both command denial and sync/local-cache tests.

The difficult implementation points are membership lookup before selecting a business, anonymous slug/token lookup, onboarding, provider event routing, worker iteration and services that commit and then query again. A one-time `SET LOCAL` in a request dependency would be insufficient after those commits. Apply validated context at each transaction boundary and prove cleanup on pooled connection reuse; PostgreSQL's transaction-local setting behavior is documented in [configuration functions](https://www.postgresql.org/docs/16/functions-admin.html#FUNCTIONS-ADMIN-SET).

## Design defaults for the plan

Start with 50-row pages and a maximum HTTP page size of 200, append a unique ID to every sort, and reset cursors on tenant/filter/sort changes. Choose keyset continuation for immutable histories; use watched local query windows for editable sorted lists so renamed/status-changed rows remain visible correctly. Infinite scrolling needs both loading/error/end state and a manual accessible continuation control.

Keep full authorized sync while measuring and fixing local queries. Do not remove historical ledger entries until all derived balances, reports and details have complete replacements. Do not migrate from current Sync Rules to newer Sync Streams solely to implement scrolling; pinned SDK/server support and preservation of old clients are prerequisites for that separate change.

The implementation plan makes these defaults concrete, maps every B01–B31 and N01–N12 finding to tasks, and defines which domain decisions must be settled before an irreversible data transformation.
