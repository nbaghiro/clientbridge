# CI review, 2026-10-12

Scope: `.github/workflows/ci.yml` on `origin/main` (at 564b040f) and PR #7 (`flake-fixes`, tip 0139ca6c). Data comes from the last 66 workflow runs on main and PRs (2026-10-10 to 2026-10-13, 70 attempts), their job and step timings from the Actions API, and the logs of every failed job (33 logs). Timings for "the current layout" use the 41 runs since the mobile sharding landed (38249596100 onwards).

## 1. How CI is structured now

One workflow, `ci`, triggered on `push` to `main` and on every `pull_request`. Concurrency group `ci-<ref>`: a new push cancels an in-flight PR run, while every main commit runs to completion (the group includes the SHA on main). There is no `permissions:` block, but the repository default for `GITHUB_TOKEN` is read-only. No job uses secrets.

Caches: setup-node pnpm store (about 505 MB, restored in 8 jobs at about 12 s each), setup-uv (it holds 97 KB, see 3.4), the APK under `apk-x86_64-<fingerprint>-<lockfile>`, Gradle via `setup-gradle` (about 2.2 GB per generation, written on main only), and the AVD snapshot (2.47 GB). Repository cache usage is 10.7 GB across 33 entries, above the default 10 GB limit, so GitHub is evicting by least recent use.

Wall-clock critical path for a typical PR: changes (0.1) then mobile-build (1.2) then the slowest shard (8.5) then the aggregator, about 10 minutes. The longest independent jobs are sync (7.2) and web (6.4), so mobile sets the pace by about 2 minutes. Measured PR run wall time: median about 10 minutes (8.8 to 17). Main runs take 10 to 20 minutes because three of the last four main runs rebuilt the native APK (38267254347, 38290597213, 38326861947; cause in section 3).

Runner time: about 58 runner-minutes per PR run (54 to 67), split roughly as mobile shards 23, sync 7, web 6.5, frontend 5, backend 4.5, site 3.5, connect 3, the rest 3. The repository is public, so these minutes are not billed; the practical limits are wall time and the 20-concurrent-job cap on the free plan (each run starts 12 jobs, which is why queue time reached 4.4 minutes when two PRs pushed together; the median is 2 seconds).

Setup work is cheap and not worth restructuring for: checkout 2 s, setup-uv 3 s, `uv sync` 2 s, `pnpm install` 4 s after a 12 s store restore, Playwright with system deps 22 s, `make seed` 22 s, `make up migrate seed` 62 s. Together this is about 5 of the 58 runner-minutes per run.

### Verdict on PR #7

PR #7 is needed. It fixes five of the six open flake causes (rows 1 to 5), and one of its changes is time-critical: backend tests hard-code 2026-11-01 and 2026-12-01 (`test_bookings_time_off.py`, `test_public_booking_online.py`, `test_public_booking_slots.py`, `test_public_manage.py`), which will start failing on main within weeks as those days enter the past or leave the booking window.

The rerun-changed-tests step is already gone at the tip (0139ca6c removes it, along with the `rerun-*` Makefile targets and the path filter, so every PR now runs every suite). While it existed it added 9.5 minutes to web, 2.3 to backend and 2.3 to connect (run 38304962328 took 24 minutes) and caused failure 9. Squash on merge so the add-then-remove history does not land on main.

Per commit:

- 70bc041b (fresh database, business-zone dates, order-independent SQL tests): keep. The dates are required. The fresh database fixes local runs that share the dev database; CI already gets a dedicated Postgres, so in CI it only costs a second migrate (about 5 s). The SQL test change has no CI failure behind it but is cheap and removes an order dependency.
- a7c1015f (HIBP off, public rate limit, offsite assets, invitee cleanup): keep the invitee cleanup (evidence in row 2). Change how HIBP is turned off: `infra/kratos/kratos.yml` is the only Kratos config in the repo, so setting `haveibeenpwned_enabled: false` there turns it off everywhere unless launch work remembers to undo it. Keep it `true` in the file and turn it off for local and CI through the environment (`SELFSERVICE_METHODS_PASSWORD_CONFIG_HAVEIBEENPWNED_ENABLED=false` in the `kratos` service in `docker-compose.yml` and as `-e` in `infra/kratos/standalone.sh`). The rate limit and offsite asset filter have no CI evidence behind them; they are harmless and can stay.
- 83a9c857 (rerun step, uv cache): the rerun part is already reverted. For the cache, prefer `enable-cache: false` on setup-uv over `prune-cache: false` in three jobs (see 3.4).
- 429e7ff0 (`useSyncStatus`) and b91f98a2 (one security settings flow): keep, both fix observed flakes.
- ea14a708 (`10.0.2.2` instead of `adb reverse`): keep; the "repeat changed e2e files" half is already gone.
- 0139ca6c (every suite on every PR, rate limit from `ENV`, `uv run`): keep. The aggregator now requires `success` for every needed job, which is correct once nothing is skipped.

What PR #7 misses: the emulator download flake (row 6, fix in 3.2), the cache over its limit (3.5), timeouts on most jobs (section 4), and the web e2e running only against the Vite dev server (section 4).

## 3. Optimizations, ranked by impact over effort

1. Overlap the API wait with emulator boot in the mobile shards. Today each shard waits for the API (median 50 s, max 71 s) before the emulator step starts, although booting from the snapshot, `adb install` and Maestro start do not need the API. Change: delete the "wait for the API" step and put `timeout 300 sh -c 'until curl -sf 127.0.0.1:8701/health; do sleep 2; done'` in the emulator `script:` after `adb install`. Saving about 45 s on the critical path of every run. Risk: low.
2. Cache the Android SDK packages and pin the emulator build. This removes flake 6 (2 failures in 25 runs) and 25 to 55 s per shard. Change: add `/usr/local/lib/android/sdk/system-images/android-34/google_apis/x86_64` and `/usr/local/lib/android/sdk/emulator` to the AVD cache paths (bump the key to `avd-34-x86_64-google_apis-v2`), and set `emulator-build:` on both android-emulator-runner steps to a fixed build so sdkmanager has nothing to fetch. If caching is unwanted, at minimum retry the emulator step once on failure. Saving about 40 s per run on the critical path plus about 8% fewer red runs. Risk: low; the cache grows by about 1.5 GB, so do it together with item 5.
3. Drop the lockfile hash from the APK cache key. The key is `apk-x86_64-<fingerprint>-<pnpm-lock hash>`, so any lockfile change forces a 6 to 8 minute native build, although the rebundle step already handles JS-only changes and the Expo fingerprint covers autolinked native module versions. Three of the last four main runs rebuilt for this reason (the playground removal changed only JS packages). Change: key on the fingerprint alone. Saving 5 to 7 minutes on most merges to main and on the first push of any PR that touches dependencies. Risk: low to medium; check once that bumping a native module's version changes the fingerprint (`fingerprint:generate` before and after).
4. Turn off the setup-uv cache. The saved cache is 97 KB because `uv cache prune --ci` removes downloaded wheels, so every job downloads its wheels anyway (`uv sync` takes 2 s). Change: `enable-cache: false` on every `astral-sh/setup-uv` step, and drop the three `prune-cache: false` lines from PR #7. Saving a cache round trip per job and the whole lock-wait failure class. Risk: none.
5. Bring the Actions cache under 10 GB. Gradle accounts for about 5.6 GB (three 1 GB `gradle-dependencies` entries and two 0.8 GB `gradle-transforms` entries), the AVD 2.5 GB and four pnpm stores 2 GB. If the AVD snapshot is evicted, all three shards rebuild it in the same run, adding several minutes each. Change: `cache-cleanup: on-success` on `gradle/actions/setup-gradle`, and consider `cache-disabled: true` there since native builds now happen only on a fingerprint change. Saving: avoids the eviction stalls. Risk: a cold native build takes a few minutes longer.
6. Rebalance or add a shard. Flow time per shard is 4.2, 4.4 and 4.8 minutes (setup 1:47 + recovery 1:28 + payments 1:00 in shard b); per-shard overhead is about 3 minutes. Moving `09-staff-pay-labels.yaml` and `08-estimate-shortcut.yaml` (35 s together) to shard a evens them out for about 20 s. A fourth shard would save about 1 minute of wall time for about 3.5 more runner-minutes. Only worth it after items 1 and 2, since sync (7.2 minutes) then becomes the critical path anyway.
7. Split `make build` out of the frontend job. Lint and unit tests take 134 s and the build 127 s in sequence. A separate `build` job would take frontend from 4.9 to about 2.8 minutes. Not on the critical path, so the only gain is quicker feedback on lint failures. Risk: none; a new required check would be needed.
8. Things not worth doing now. Deduplicating stack setup (seeded database snapshots, shared docker images) saves well under a minute per job and none of it is on the critical path. Starting shards before the APK exists would save the 1.2 minute build only through artifact polling, which is fragile. pytest-xdist for backend (3 minutes of pytest) and more Playwright workers for web would speed jobs that do not set the wall time. Path filters are not recommended: the user prefers full runs, the runner minutes are free on a public repository, and the old filter already matched `backend/**` and `frontend/packages/**`, so it skipped little.

With items 1 to 3, a typical PR run should drop from about 10 to about 8.5 minutes (then bounded by sync), and main runs from 15 to 20 minutes to about 9.

## 4. Correctness and hygiene

- Missing timeouts. Only sync (15), web (30), mobile-build (40) and mobile shards (30) set `timeout-minutes`. backend, contract, frontend, site, connect, codegen-drift, changes and the aggregator default to 360 minutes; a hung pytest or Playwright server would hold a runner for six hours (run 38083697551 ran 75 minutes before it was cancelled). Add 15 to backend, frontend, site and connect, and 5 to contract, codegen-drift, changes and the aggregator.
- setup-uv activates the wrong environment. With `python-version: "3.14"`, setup-uv v5 creates and activates `.venv` at the repository root, so every `uv run` in `backend/` warns that `VIRTUAL_ENV=.../clientbridge/.venv does not match the project environment path .venv`. The root venv is unused. Drop `python-version` (uv reads `backend/.python-version`, which already says 3.14) or set `working-directory: backend` on setup-uv. This also removes a second place that names the Python version.
- Inline environment variables. `STRIPE_MOCK_URL=http://localhost:8708` in the contract job and in `make test-contract` repeats the default in `tests/contract/conftest.py`; remove both. `SMTP_URL=smtp://localhost:8716` is inline on the uvicorn command in web and the mobile shards and as a shell default in `make dev-api`; make it the `ENV=dev` default in `Settings` (or a job-level `env:` entry) so every way of starting the API agrees. PR #7's mobile-build moves its variables to a job `env:` block, which is the right form.
- Two Postgres builds in CI. backend and connect use the floating service image `postgres:16`, while web, sync and the mobile shards use the digest pinned in `docker-compose.yml`. Use the same digest for the service containers.
- Unpinned dependencies that can turn CI red without a code change: `rustfs/rustfs:latest` and `stripemock/stripe-mock:latest` (both in compose and as services), `redis:7`, Maestro installed from `get.maestro.mobile.dev` at whatever version is current (set `MAESTRO_VERSION`), and the "latest emulator" that android-emulator-runner installs (item 3.2). Actions are pinned to major tags, which is acceptable for first-party actions; consider SHA pins for `dorny/paths-filter` (removed by PR #7), `reactivecircus/android-emulator-runner` and `astral-sh/setup-uv`.
- Ways CI can be green while something is broken:
  - `make test-kratos` and the contract tests skip, rather than fail, when their service is unreachable. CI checks readiness first, so this has not happened, but a crash between the readiness check and the tests would pass silently. A simple guard is to fail the step when the summary reports any skip for `-m kratos`, and to expect exactly the four known contract skips (stripe-mock does not implement Account Sessions, so `create_account_session` is never exercised in CI).
  - The web and Connect e2e suites run against `vite` dev servers, not the production bundle that `make build` produces in the frontend job, so a bundle that builds but breaks at runtime (chunking, env replacement, minification) is not exercised by any browser test. The site suite already uses `vite preview`; consider the same for web and Connect, which would also remove StrictMode double effects from e2e (flake 3).
  - The ruleset's `strict_required_status_checks_policy` is false, so a PR can merge after main has moved without a rerun against the new main. The main push run catches the result afterwards (as it did for 38210679166). Turning it on costs a rerun per merge when main is busy; leaving it off is a reasonable choice as long as main failures are fixed promptly.
- Required checks match the job names: backend, contract, frontend, site, connect, codegen-drift, sync, web, mobile all exist on main and on PR #7. The removed `playground` job was never required. PR #7's rename of `changes` to `shards` does not affect required checks.
- Diagnostics: backend prints the full coverage table (about 190 lines) on every run; `--cov-report=term:skip-covered` would shorten it. The mobile shards did not print Kratos logs before PR #7, which is why flake 4's cause cannot be confirmed from CI.
- Secrets: none are used, and Kratos dev secrets in `standalone.sh` are labelled as dev-only defaults. Workflow token permissions default to read at the repository level; adding `permissions: contents: read` at the top of `ci.yml` keeps that true if the repository setting changes.

## Summary of recommended changes

1. Merge PR #7 (squashed), after moving the HIBP switch to an environment override and replacing `prune-cache: false` with `enable-cache: false`.
2. In a follow-up CI change: move the API wait into the emulator script, cache the SDK system image and emulator with a pinned `emulator-build`, key the APK on the fingerprint only, enable Gradle cache cleanup, and add `timeout-minutes` to every job.
3. Hygiene: drop `python-version` from setup-uv, remove the redundant `STRIPE_MOCK_URL`, move `SMTP_URL` into settings, pin the Postgres service, rustfs, stripe-mock and Maestro versions, and decide whether web and Connect e2e should run against a production build.
