Orientation

The big picture

Clientbridge is offline-first: every device holds a tenant-scoped SQLite replica kept live by PowerSync. Screens read that local replica instantly; writes travel back to the server, which owns every invariant. The repo is a clean polyglot split — each ecosystem idiomatic — joined only by generated artifacts.

backend/ · Python

uv · FastAPI · async SQLAlchemy · Postgres · Alembic · arq jobs · Stripe Connect. Layer-first, one file per domain, per layer.

frontend/ · TypeScript

pnpm + turbo monorepo. Three apps (web, mobile, connect) over five @clientbridge/* packages. Share the view-model, render per platform.

infra/ · Ops

Docker Compose (Postgres · PowerSync · Redis · MinIO), PowerSync service config + read-authorization sync rules, on the 87xx port block.

.docs/ · Specs

Three consolidated docs — architecture, engineering, roadmap — plus the design explorers that generate the theme.

The boundary is crossed by exactly three bridges

No source is shared between Python and TypeScript. Everything that must agree is generated from a single source, with a CI drift gate that fails if the committed output diverges.

Orientation

The 5 surfaces

Every capability is exactly one of five surfaces. The rule that decides which: a server-only invariant — numbering, capacity, money, secrets, uniqueness, cross-tenant — must be a command, never a sync-write.

surface 1

Sync-read

PowerSync streams a scoped SQLite replica per device. Screens useQuery it. Server-only tables are excluded from the client schema.

surface 2

Sync-write

POST /sync/upload gated by WRITE_POLICY — only low-risk, client-owned tables; role + ownership + no-cross-tenant + field allowlist enforced.

surface 3

Command / RPC

FastAPI POST/PATCH/DELETE under /v1/*, each wrapped in run_command — atomic + audited + idempotency-replay. Home of every invariant.

surface 4

Webhook / public

api/webhooks.py (Stripe/Interac/SMS, signature-verified) + api/public.py (book/pay/form/contract/review, token-authed, rate-limited).

surface 5

Job

The arq worker — reminders, reap-unpaid, due broadcasts, overdue sweep, review requests, daily maintenance. Idempotent; each opens its own session.

How a request flows through the backend

HTTP→ api/v1/…→ schemas/ (DTO)→ services/ (logic + txn)→ core/scoping · command→ models/→ Postgres→ WAL→ PowerSync→ device

Routers are thin and never query — they resolve dependencies, construct a Service(db, principal, …), call one method with the validated DTO, and return a response schema. All querying and the transaction live in the service. Any raised AppError renders as {error, message} with the subclass's status.

Backend · Python

Entry & the cross-cutting core

main.py is the app factory: create_app() builds the FastAPI app, registers the single AppError handler and CORS, then mounts the routers — /auth, /sync, /webhooks, the five public routers, and /v1/*. Everything domain-agnostic lives in core/.

FileResponsibility
core/command.pyThe command wrapper. run_command(db, principal, action, run, response_model, idempotency_key) — replays a stored response for a repeated key, stages Command.record(...) audit rows, then commits mutation + audit + idempotency key as one atomic unit (rollback on any error).
core/scoping.pyThe one place the tenancy filter lives: scoped(Model, business_id, soft_delete=…) plus scoped_page/scoped_count/scoped_update/scoped_delete and the Page[T] envelope. Services never hand-write a business_id filter.
core/deps.pyDI hub: DB session, adapter aliases (EmailDep, GatewayDep, StorageDep…), the auth chain (current_principal re-derives business/role from the DB every request, honoring X-Business-Id), and role gates (assert_role per-method, require_role per-router).
core/config.pyPydantic-settings. Fails closed in prod: refuses to boot if the JWT secret is still the dev default or the Stripe webhook secret is empty when env != dev.
core/security.pyArgon2 password hashing, SHA-256 opaque-token hashing, HS256 access tokens, and the PowerSync token (HS256 or RS256 + a JWKS endpoint for prod).
core/ids.pyPrefixed-ULID PKs (bz_…, bk_…). Time-sortable, so scoped_page can order id DESC for newest-first.
core/errors.pyAppError taxonomy → HTTP status (NotFound 404, Conflict 409, CardDeclined 402, TooManyRequests 429…).
core/ratelimit.pyIn-process fixed-window limiter for the five public surfaces (30/60s each).
core/db.pyAsync engine + SessionLocal + the Base metadata that sync/upload.py reflects over.

models/ — the 10 domains

SQLAlchemy, one file per domain. base.py holds mixins only (PKMixin, TimestampMixin, BusinessScoped, SoftDelete, enum_check). No relationship() appears anywhere — so the unit-of-work can't FK-order inserts, and services flush the parent before its FK children.

Backend · Python

schemas/ — the DTOs

23 Pydantic files, fanned out finer than models — billing.py covers invoices + estimates + lines, and several are per-surface (public_booking, dashboard, payouts).

  • Requests name by verb: *Create/*Update, *Patch, *Body (auth), *Send/*Purchase/*Redeem. Validation via Field(ge=…), Literal[…] enums, and @field_validator/@model_validator.
  • Responses are *Out — mostly hand-mapped by service _out(...) builders; a few opt into from_attributes=True.
  • Public Public* DTOs are deliberately slim projections for the unauthenticated surfaces.

Backend · Python

services/ — the brain

~40 files, one per domain concern. The rule of thumb: money / uniqueness / cross-tenant paths go through run_command; plain CRUD (catalog, client) just uses scoped() + db.commit(). Admin-only methods call assert_role(...).

Scheduling — four files, two easily confused

availability_servicePure helpers: open_windows (date rows override weekday rows; None=unrestricted, []=closed) + tz-aware is_within_availability (uses business_tz from business_service).
scheduling_serviceRead-only slot enumerator — open_slots(...) steps open windows by duration+buffers and drops conflicts. The read mirror of the write invariant.
schedule_serviceRecurring series. expand_occurrences (RRULE-lite, 60 cap) then one booking per occurrence in a savepoint each, re-localized per date to survive DST. A command.
booking_serviceThe invariant's home. create_booking_core takes a pg_advisory_xact_lock(business:staff), checks availability, increments class capacity or asserts a free slot; a GiST exclusion constraint backstops concurrent overlap → Conflict.

Billing, POS & tax

billing_serviceInvoice + estimate lifecycle (create/update/send/void/accept/decline/convert) — 10 commands; per-business numbering.
linesShared parent-agnostic line + tax engine (replace_lines, tax_for_lines) reused by invoices, estimates, orders.
order_servicePOS Order: create (any staff) / void (admin) / checkout (Terminal) / connection_token — per-method role variance.
tax_service · tax_ratesPure, no DB. Line-level GST/HST/PST/QST (QST at exact 9.975%, half-up rounding, small-supplier collects nothing); rates hardcoded per province. Golden-tested.
report_service · dashboard_serviceRead aggregates + CSV (income, GST/HST return, T4A) · the "Today" money tiles.

Payments — the money core

payment_service.py is the largest file in the repo (~1680 lines): a PaymentService class (onboarding, pay_invoice, card/PAD setup, refund_payment, Interac) plus a body of module-level webhook + helper functions.

  • Refund guards over-refund — blocks refunding a partly-redeemed gift card or a package with sessions used; reverses deposit + entitlement, recomputes client LTV.
  • open_* builders (card / booking-deposit / entitlement / terminal / interac) are Stripe-idempotency-keyed + provider_ref-deduped, shared by services and the public surfaces.
  • Webhook _dispatch routes payment/refund/dispute/payout, KYC mirror, and the full recurring-billing lifecycle; payout allocations split each paid booking line to its payee staff, idempotently.
payout_serviceManual allocation lifecycle: approve → pay. Admin, commands.
subscription_serviceCreate (lazily mints a recurring Stripe price, one-active guard) / cancel.
package_service · gift_card_servicePurchase via open_entitlement_payment (pending until the webhook settles) / consume-or-redeem under a with_for_update lock so concurrent draws can't double-spend.

Documents, reviews, messaging & files

contract_service · form_serviceEach send_* mints a token'd row and notifies inside the command, so a same-key retry replays without re-sending.
file_serviceMints a server-keyed File + presigned upload URL — the S3 key derives from the resolved business, never the caller.
message_serviceTwo-way conversational messaging: send / broadcast / mark-read + inbound-SMS webhook (SID dedup) + due-broadcast cron.
notification_serviceOne-way event notifications — a Notifier with ~24 on_* handlers, and the English copy builders that are the single home of backend copy.
public_* (6)Unauthenticated surface — booking / pay / form / contract / review + public_common. No principal; an opaque token or slug scopes to one business.
Service shapes: a XxxService(db, principal) class holds the request-scoped handlers (they need the principal + own the transaction); module-level functions hold everything called outside a single authed request — shared cores (create_booking_core), webhook/job processors, pure helpers (business_tz, tax math), and the private _out DTO mappers.

Backend · Python

api/ — thin routers

api/router.py mounts 25 domain routers under /v1. Every one is DTO-only and delegates to a service; mutations thread the Idempotency-Key header into run_command. Uniformly-admin routers gate once with AdminPrincipal = require_role("owner","admin").

Authed · /v1/*

auth · business · catalog · clients · bookings · schedules · invoices · estimates · orders · terminal · payments · payouts · packages · subscriptions · gift-cards · forms · contracts · files · messaging · reviews · reports · tax · dashboard · devices · staff · onboarding.

Public · api/public.py

Five token/slug-authed, rate-limited routers — /book · /pay · /form · /contract · /review.

Webhooks · api/webhooks.py

Stripe (signature-verified) · Interac + SMS (constant-time shared secret). Notifications fire post-commit so a delivery failure can't roll back a settlement.

Backend · Python

sync/ — the server-authoritative write path

sync/auth.py exchanges the app JWT for a short-lived PowerSync token and serves the RS256 JWKS. sync/upload.py is where PowerSync's client queue lands — the enforcement layer for what a device may write.

WRITE_POLICY is an allowlist mapping table → (min_tier, own_only). Only clients, subjects, notes, messages, availability (own-only), and the admin-writable items/resources/forms/contracts are sync-writable. Everything money/capacity/secret is excluded, with a comment naming the server-only invariant behind each. Each op is authorized by role + ownership, blocked from cross-tenant moves, stripped of SYSTEM_FIELDS + COMMAND_ONLY_FIELDS, then applied in one transaction.

Every external service is a typing.Protocol + a prod implementation + a get_*() dependency that tests override with a recording fake — so the boundary is covered without the network.

Backend · Python

migrations

Alembic: the source of truth is the models; the chain is a squashed initial (36 tables, 75 indexes, 41 CHECKs) + 28 strictly-linear hand-tuned increments. Concurrency invariants live in SQL — GiST exclusion constraints stop double-booking; partial-unique indexes enforce business rules (one active subscription, one open review request, one refund per payment).

Backend · Python

tests & the gate

Integration-first: httpx → the real FastAPI app → a real migrated + seeded Postgres. Unit tests are reserved for pure logic. "Don't mock our code" — only external boundaries are faked.

The fixture spine

conftest.py: a transactional-rollback-per-test session, auth clients as_owner/as_staff/unauth, boundary fakes (email/SMS/push/storage/oauth + an in-memory Stripe gateway that honors idempotency keys), and a Factory for multi-tenant isolation tests.

The seed baseline

scripts/seed_demo.py builds "Birchbark Pet Studio" (owner us_dev) — the committed fixture every integration test asserts against. ~300 rows exercising every implemented surface, TRUNCATE-then-insert, FK-safe.

Three Stripe test tiers: the in-memory fake (fast, hermetic, the default run) → stripe-mock (the real adapter validated against Stripe's OpenAPI spec, tests/contract/) → real test-mode Stripe with a Test Clock (tests/e2e/, skipped without keys). The gate: ruff + ruff format + mypy --strict + pytest --cov-branch --cov-fail-under=90, on Python 3.14.

Cross-cutting patterns

The handful of ideas that, once internalized, explain most files.

Tenancy has one home

Every tenant query goes through core/scoping.scoped(...). A business_id filter is never hand-written; Principal.business_id is re-derived from the DB each request, never trusted from the token.

Invariants are commands

run_command makes money/uniqueness/cross-tenant mutations atomic + audited + idempotent. Anything a client shouldn't forge is a command, not a sync-write.

Generate, don't share

Python and TS share no source. The sync schema, API client, and design tokens are generated from a single source with a CI drift gate.

Copy lives in one place each

All UI copy is in strings.ts (lint-enforced); all backend copy is in notification_service.py. Both are the single home of copy.

The lean bundle is enforced

Connect's PowerSync-free carve-out is real: a separate public.ts entry, optional peer deps, and an ESLint no-restricted-imports boundary with CI teeth.

No relationships → flush order

Models declare no relationship(), so services flush a parent before its FK children and the seed hand-orders inserts. IDs are prefixed ULIDs — time-sortable, powering newest-first paging.
