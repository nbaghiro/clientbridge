# Native walkthroughs

These Maestro flows open a release build of the Clientbridge iOS/Android app against a run's own API on the shared test tier. They are separate from the React Native Web component previews.

## Run

The native lane runs every flow on a release build against the shared test tier (`make test-tier`), under the run's own namespace, the same way the browser lanes do. Build the e2e app once per native change (about 8 minutes for iOS and 10 for Android here), then run the lane on a device that is already started:

```sh
make test-functional FUNCTIONAL_ARGS="--build-native ios"
make test-functional FUNCTIONAL_ARGS="--surface native --platform ios --device <simulator-udid>"
make test-functional FUNCTIONAL_ARGS="--build-native android"
make test-functional FUNCTIONAL_ARGS="--surface native --platform android --device emulator-5554"
```

Without flow names the lane runs every flow in file-name order; name flow files after the arguments to run only those, for example `... --device <udid> clients.yaml`. The build is `ca.clientbridge.app.e2e` ("Clientbridge E2E"), so a development build and its data stay untouched; the lane installs it fresh, and uninstalls it when it finishes. The build has `127.0.0.1` (iOS) or the emulator's `10.0.2.2` (Android) on ports 8794, 8795 and 8796 compiled in, and the lane forwards those to the run's API and the tier's auth and PowerSync, so no `adb reverse` is needed. Because those ports and Maestro's driver port 8797 are fixed, one native run at a time holds them. The lane never starts, boots or shuts down a device.

Flows tagged `lane` call `helpers/control.js`, which asks the lane to cut the forwarded services (`offline`), restore them (`online`), deliver a push (`push`) or put the run's business in a payment account state (`account`, with `paused`, `due`, `declined`, `foreign` or `ready`), as Stripe's events would on a lane that has no Stripe keys. It also adds a flow asset to the phone's photo library (`photo`), which Maestro's `addMedia` can't do for a HEIC, gives an account a software security key (`key`), and returns an authenticator code for a secret (`totp`), since Maestro's scripts have no crypto, finishes a bank authorization on the stand-in Stripe (`bank`), and texts the run's business from a phone number, signed as Twilio signs it (`text-in`, with `"<phone> <words>"`). `helpers/client-files.js` asks the lane for a client's committed notes (`notes`) and starts or finishes a client photo upload as the web does (`client-photo`), answering with what the server holds. Going offline this way leaves the device's own network alone, unlike airplane mode, so a shared emulator stays usable. Flows tagged `ios` run only on iOS. Flows tagged `stripe` need Stripe, which the lane doesn't have: the default run leaves them out, and `--fake-stripe` runs only them, with the API pointed at `backend/e2e/stripe_fake.py`. That stand-in answers creating a customer and the bank debit capability, and refuses and logs any other call in `stripe-fake.log`, so a flow that needs more fails visibly (`make test-mobile PLATFORM=ios DEVICE=<udid> ARGS="--fake-stripe"`). The lane passes `APP_ID`, `E2E_NAMESPACE`, `MAILPIT_URL`, `AUTH_ADMIN_URL` and `CONTROL_URL`; the flows stop with an error when one is missing. Every run has its own copy of the core demo businesses, so the logins carry its namespace (`hannah+<namespace>@birchbark.example`), and a throwaway recovery login does too, which is how the tier routes its reset mail to the run.

The reports land in `.scratchpad/e2e-<id>/`: `native-results.xml` (JUnit, checked against the cases `backend/e2e/cases.json` registers for the platform), `native-artifacts/` screenshots, `native-debug/` Maestro and XCUITest logs, and `control.log`.

On iOS the lane restarts the simulator's pasteboard daemon first. A stuck `pasted` blocks the app's main thread whenever a text field takes focus, which Maestro reports as `Unable to perform work on main run loop, process main thread busy for 30.0s`; that was the earlier iOS keyboard failure, not an app fault.

`make test-mobile PLATFORM=ios DEVICE=<udid>` runs the same lane. The demo users are Hannah (owner) and Diego (staff), both using `demo1234`.

## Flows on real Stripe

`stripe/` holds the flows that reach the Stripe sandbox. The native lanes can't run them: the phone's card form talks to Stripe directly, so the stand-in can't answer it. The Stripe lane runs them instead, with its sandbox credentials, its leased QA merchant, `stripe listen` and the cleanup that refunds or detaches what a run made. They need an e2e build with the sandbox's publishable key, kept apart from the regular build (`.scratchpad/native/ClientbridgeE2E-stripe.app`), and the lane refuses a build compiled with another key. Build it once per native change, then run the flows on a started device:

```sh
cd backend && uv run python -m e2e.stripe native-build ios
make test-stripe-native PLATFORM=ios DEVICE=<simulator-udid>
```

These flows call `control.js` with `purchaser`, which files the flow's client with the lane before the app gives it a Stripe customer, so the lane's cleanup owns what the flow saves, and `helpers/stripe-wallet.js`, which reads the client's saved methods as the app recorded them and as Stripe holds them, or `helpers/stripe-money.js`, which waits until the client's payments read as expected and the books hold Stripe's net and fees, then returns both sides with the Payouts figures. The e2e build discovers Stripe Terminal's simulated Tap to Pay reader, which on iOS shows Stripe's own sheet with Tap to Simulate Payment and a close button; the simulated reader declines an amount ending in 05 cents. CI doesn't run them yet.

Flows assert meaningful visible controls/content, then capture screenshots. The modal checks protect the regression where the accessible backdrop parent hid every sheet descendant from iOS's accessibility tree. The Inbox entry also relies on its explicit accessible name.

The helpers launch the app, wait for authentication/sync, and dismiss React Native's development warning banner when present because it covers the bottom navigation. That dismissal uses a point inside the **identified banner**, not a fixed screen coordinate. The staff email entry taps near the end of the input before erasing and asserts the resulting address, since a center tap can leave trailing characters after iOS backspacing. Closing a sheet similarly targets its named backdrop near the upper edge. Other navigation uses labels and relative selectors; horizontal tab scrolling starts from a visible tab. A full-width row scrolled into view on a tab screen uses `centerElement: true` before it is tapped, since a row that only just reaches the bottom edge sits under the raised new button and the tap opens the new menu instead. These techniques follow Maestro's [tap](https://docs.maestro.dev/reference/commands-available/tapon) and [swipe](https://docs.maestro.dev/reference/commands-available/swipe) APIs.

Apart from the client that `clients.yaml` creates, the logo and cover that `setup.brand.yaml` saves, the catalog items that `entitlements.yaml` adds, the gift card `entitlements.giftcards.yaml` sells and spends, the two online requests `bookings.requests.yaml` answers, the cash sale with its items that `pos.discounts.yaml` rings up and the seeded online order S-5 that `pos.pickup.yaml` hands over and the estimate `billing.estimates.yaml` sends and converts, the suite does not submit business forms, messages, broadcasts or payments, or deliberately change bookings, inventory, tax or staff pay. It does sign users in/out and may update local notification seen state. It does not clear app data or the system keychain. An unexpected unsynced-changes confirmation is not approved by the tests. Use a dedicated development device; the staff flow changes its session and restores Hannah after completion.

## Known regressions

`regressions/client-editor.yaml` reproduces the client-record Edit transition and expects the editor to appear. It passes on iOS and Android release builds (November 2, 2026), and folding it into the default suite is `NATIVE-CRM-02`:

```sh
maestro --device <simulator-udid> test e2e/regressions/client-editor.yaml \
  --test-output-dir test-results/regressions --format HTML \
  --output test-results/regressions/index.html
```

The Create → Estimate shortcut (`billing.yaml`), the Staff pay total labels (`earnings.yaml`) and inbox navigation (`messaging.navigation.yaml`) were fixed on October 10, 2026 and run with the default suite.

## Boundaries

These are navigation and composition walkthroughs, not exhaustive transaction tests. Real card charging, terminal hardware, push delivery/taps, second factors on the device, fresh-business onboarding, offline reconnect/conflicts, every empty/error state, release builds, iPad layout and further Android device/OS combinations require additional runs. Passing browser “iPhone/Android” frames does not cover those native concerns.

## Sync startup regression

`offline.hours.yaml` verifies saved-session restoration, selection of the scoped business, and the recurring-hours editor on the actual native app without submitting a business change. The owner helper waits for the asynchronously loaded viewer name.

Use normal simulator signing when building iOS. A build produced with signing disabled can make SecureStore fail with a missing Keychain entitlement before the replica opens. Rebuilding/installing the same bundle with normal signing preserves app data; deleting the database does not resolve this credential-storage failure.
